# 打字机身份参与样式判等

打字机数据住在 mixin 给 `Style` 加的隐藏字段里，而原版 `Style.equals` 只比那十个原版字段，于是"只差打字机参数"的两个样式被判为相等：物品会堆叠（堆叠时只保留其中一份的数据，另一份静默丢失）、聊天栏的连续消息会被并成一条 "2x"。因此在原版判等返回 true 时补一次打字机身份比较，身份**只看出字速度与逐字指令**。

## Considered Options

- **把 `session` 也算进身份**：`session` 是解码时随机生成的，同一段 JSON 生成的两件物品 `session` 也不同，算进去会让本该堆叠的物品永远堆不起来，**不采用**。
- **不动判等、只在文档里说明**：用户会持续面对"看着一模一样、行为却不同"的物品，而且堆叠会静默丢数据，代价比改判等更大，**不采用**。

## Consequences

- 判等只会变得更严格。原版两处与 `EMPTY` 的比较（`Style.create` 的折叠、`checkEmptyAfterChange`）都发生在打字机数据挂上去之前，因此不受影响。
- `hashCode` 不动：相等的样式必然仍满足原版的哈希一致要求；不相等的样式哈希相撞是合法情形。
- 注入点落在原版 `Style` 上，其他模组若依赖"带打字机的样式与空样式相等"这个本来就不可见的前提，行为会变。
- 判等只解决“两者能不能算同一个”。样式被改写时打字机数据仍可能丢：`Style.applyTo` 一类（含 `withStyle(非空样式)` 与 `Component.visit` 的样式合并）已在同一批改动里补上了状态传递；但 `withColor`、`withBold`、`applyFormat` 这些**逐字段另造 Style** 的方法带不上隐藏字段——这是把数据挂在样式隐藏字段上的固有代价，见 README 的已知限制。
